# The bottom of the screen on an iPhone

This document exists because one question has been asked and answered wrongly
several times: **"why is there a grey/black bar under the navigation, and how do
we remove it?"**

The short answer:

> In a normal Safari tab, almost all of it is Safari's own URL field and button
> bar. It is not the app's, and no amount of CSS in this repository can reclaim
> it. Adding Fantasy Analyst to the iPhone Home Screen and launching it from
> that icon *does* reclaim it, because a Home Screen web app runs without
> Safari's chrome. That is the fix, and it is implemented.

Everything below is the evidence and the mechanics.

---

## 1. Who owns which pixels

A webpage in a Safari tab is given a *visual viewport*. Safari keeps what is
left for itself. From the top of the screen down:

| Region | Owner |
| --- | --- |
| Status bar (clock, battery) | iOS |
| Safari's URL field and toolbar (top, when expanded) | Safari |
| **The page — `window.innerHeight` worth of it** | **this app** |
| Safari's bottom button bar and URL field | Safari |
| Home indicator | iOS |

The app owns exactly one of those rows. The only number that says whether the
app is holding space it should not is:

```js
window.innerHeight - document.querySelector('.tabbar').getBoundingClientRect().bottom
```

**That number should equal `--toolbar-gap`, and nothing more.** The navigation
is a floating pill rather than a band welded to the bottom edge, so it
deliberately sits clear of the last pixel; the gap is a number the design
chooses, and on a screen with a home indicator it is what keeps the destinations
off it. Anything *above* that gap is the page holding space it should not, and
is a real bug.

The claim used to be "this number is zero". Read that in older commit messages
as the same claim with a different constant: the bar spent the indicator's
clearance as padding inside itself, and now spends it as distance underneath.
What has never been allowed is a second consumer of the inset.

That equality holds at a simulated home-indicator inset of both 0px and 34px, at
390/375/360 wide, in Light and Dark, in a browser tab and in simulated
standalone mode. It is asserted by [`e2e/app.spec.ts`](../e2e/app.spec.ts) ("the
floating toolbar"), [`e2e/toolbar.spec.ts`](../e2e/toolbar.spec.ts) and
[`e2e/pwa.spec.ts`](../e2e/pwa.spec.ts), and it can be read off the phone itself
under **Setup → Install on iPhone → Layout diagnostics**, which prints both the
measurement and the gap it is supposed to be.

So: no page-owned surplus exists. Prior passes that changed CSS to close one were
adjusting a number that was already correct.

## 2. What not to do about Safari's chrome

Do not try to remove it. Specifically, do not add:

- negative margins that pull content under the browser bar;
- offsets hardcoded to one iPhone's toolbar height;
- `100vh` tricks that make the page taller than the viewport;
- the old "scroll by one pixel to collapse the toolbar" hack;
- a fake fullscreen mode in JavaScript.

Each of these trades a working app for a few pixels the browser is entitled to,
and each breaks differently when Safari's chrome expands, collapses or changes
size in a future iOS.

## 3. The actual fix: a Home Screen web app

A site with a web app manifest whose `display` is `standalone` can be added to
the Home Screen and launched as an app. In that mode there is no URL field and
no browser button bar — the app gets everything except the system status bar and
the home indicator.

Installed here as:

- [`src/web/public/manifest.webmanifest`](../src/web/public/manifest.webmanifest)
  — `display: standalone`, `start_url: /`, `scope: /`, icons, launch colours;
- icons generated by [`scripts/make-icons.mjs`](../scripts/make-icons.mjs) — the
  ◈ from the Draft tab, in the dark theme's accent, at 192/512/512-maskable plus
  a 180px `apple-touch-icon` (Safari uses that one for the Home Screen);
- metadata in [`src/web/index.html`](../src/web/index.html) — the manifest link,
  both spellings of the web-app capability tag, the status bar style, and
  `viewport-fit=cover`.

**How to install it** (this is also in the app, under Setup):

1. Open the site in Safari on the iPhone.
2. Tap the Share button — the square with an arrow.
3. Choose **Add to Home Screen**.
4. Launch Fantasy Analyst from the new icon.

There is no way for the page to do this for the user. iOS has no
`beforeinstallprompt`; the Share sheet belongs to the user. The app offers a
one-time compact prompt with these instructions and nothing more.

## 4. Standalone is not "fullscreen"

Even as a Home Screen app, iOS keeps the status bar at the top and the home
indicator at the bottom. That is the platform's, it is correct, and the app pads
for it. What goes away is *Safari's* chrome. Describe the result as a
**standalone Home Screen web app**, never as fullscreen.

## 5. Safe-area ownership

`env(safe-area-inset-*)` is read in exactly one place in the stylesheet — the
`--safe-top` / `--safe-bottom` tokens — and each is consumed in exactly one
rule. Adding a second consumer is how a blank strip appears, because both
consumers are individually reasonable and the sum is not.

| Concern | Owner | Rule |
| --- | --- | --- |
| Viewport height | `#root` | `min-height: 100dvh`, and nothing else claims it |
| Home-indicator clearance | `.tabbar` | `bottom: var(--toolbar-gap)` |
| Space reserved for the bar | `.app-main` | `padding-bottom: var(--content-inset)` |
| Status bar / notch clearance | `.app-main` | `padding-top: calc(var(--safe-top) + …)` |

Three details worth keeping:

- `--toolbar-height` is **measured from the bar at runtime** (see
  `useToolbarHeight` in [`src/web/App.tsx`](../src/web/App.tsx)) and is the pill
  *only*. Measuring its whole reach instead would be measuring a transform: the
  bar translates itself off screen when the keyboard opens, and the page's
  reservation would collapse with it.
- `--content-inset` is **the one place** the bar's height and the gap under it
  are added together, and `.app-main` is the only thing that spends it. The page
  must never add the device inset again on top — doing so was worth 34px of
  blank page, and was one of the bugs mistaken for Safari's toolbar.
- `--nav-inset`, which `--toolbar-gap` is built from, is deliberately **less**
  than the full inset. iOS offers 34px; the home indicator is a 5px pill sitting
  8px off the bottom edge, so 17px clears it. Spending all 34px lifts the bar
  20px higher than it needs to be, and that surplus is itself a grey strip. The
  token is capped by the device's inset, so a device without one gets a 6px
  hairline gap and nothing more.

## 6. Detecting standalone mode

One module: [`src/web/standalone.ts`](../src/web/standalone.ts). Nothing else in
the app sniffs a user agent or a media query for this.

```js
isStandalone(window)   // display-mode: standalone | fullscreen, or navigator.standalone
isIosDevice(window)    // iPhone/iPad, including iPadOS claiming to be a Mac
shouldOfferInstall(window)  // iOS, not installed, not dismissed
```

Both signals are read because they belong to different eras of iOS:
`display-mode` is the standard one current iOS sets, and `navigator.standalone`
is Apple's original flag that older devices still answer with. Believing a
stale "no" would mean showing install instructions to somebody who has already
installed.

Standalone state is used for exactly two things: whether to offer the install
prompt, and whether to offer the interactive back gesture (§9). There is no
second layout and no second UI: the safe-area rules above are written against
the device's insets, which is what actually differs between the two modes, so
they are correct in both without asking which one is running.

## 9. The edge-swipe back gesture, and why only in standalone

A pushed screen — a player's detail, one of Setup's areas — can be dragged away
from the leading edge to go back, and it follows the finger while you do it.
This is enabled **only when the app is running from the Home Screen**, and that
is a correctness decision rather than a taste one:

> In a Safari tab, the left screen edge is already Safari's own back gesture.
> Two navigations from one swipe is worse than no gesture at all, and a page
> cannot reliably take that edge from the browser without calling
> `preventDefault` on touches across a region the user also needs for
> scrolling. In a tab, the browser's gesture is left alone and the Back control
> is the answer.

The rules, all in [`src/web/gestures.ts`](../src/web/gestures.ts) and unit-tested
in `tests/gestures.test.ts`:

| Rule | Value |
| --- | --- |
| Where it may start | within 28px of the leading edge |
| Before any decision is made | 8px of movement |
| To count as a swipe rather than a scroll | horizontal > vertical × 1.4 |
| To complete the navigation | 32% of the layer's width, **or** 0.45 px/ms |
| Speed is measured over | the last 120ms of movement |
| Otherwise | springs back |

**Three things refuse the gesture before any of that is asked**, and each was a
defect first. A touch in the strip is not a back swipe when:

- **a layer is over the app.** `useAppIsCovered()`, the same signal
  `usePullToRefresh` refuses on (§10). Review renders the scoring key as a sheet
  *inside its own pushed screen*, and React portals move a layer's elements to
  the end of the document while leaving its events propagating up the component
  tree — so a finger on that card arrived at the pushed screen's handlers as
  though it had landed on the screen behind it. A sideways drag on an open sheet
  is not a dismissal (a dismissal must be downward), so it navigated instead, and
  the reader was left holding a card over the wrong page.
- **it landed in a horizontal scroller that has been scrolled.** A pushed screen
  is full-bleed and gives the page gutter back as padding, so a segmented control
  inside one starts 12px from the glass — inside the 28px strip. Swiping the
  position filter back along was also starting a navigation. The question asked
  is `scrollLeft > 0`, not "is this a carousel": a scroller already at its start
  has nothing to lose and hands the gesture over, which is what iOS does too.
- **it landed in a text field**, where dragging moves the caret and selects.

Two properties matter more than any of the numbers:

- **Scrolling wins.** The layer carries `touch-action: pan-y`, so the browser
  arbitrates: a vertical drag scrolls and cancels the gesture through
  `pointercancel`. Nothing on the page — this gesture, pull-to-refresh, the
  queue's reorder — calls `preventDefault` on a touch. The one exception is a
  modal sheet, and it is described precisely in §10.
- **Back is navigation, never undo.** The gesture calls the same function the
  Back control calls. It cannot undo a draft selection, a My Guy level, a
  filter or anything else that is stored, and it pushes no history state of its
  own — opening and leaving a detail screen leaves `history.length` unchanged.

One more thing that is not a threshold: **a swipe that springs back does not eat
the reader's next tap.** The gesture suppresses the click at the end of a drag so
that letting go over a control does not also press it; that suppression is armed
and cleared at `pointerdown`. It used to be cleared only by the click it
swallowed — which is the difference between a mouse and a thumb, because a touch
drag that springs back produces no click at all. The flag stayed raised and ate a
real tap seconds later. Nothing in a mouse-driven suite can see this; the test
that holds it injects real touch points (`navigation.spec.ts`).

There is deliberately **no swipe between the bottom tabs**: they sit above
horizontal controls (the position filter, the metric rows) and an accidental
sideways drag would navigate. Tabs are tapped.

## 10. Sheets: swipe to dismiss

Every sheet in the app is the one `Sheet` component
([`src/web/components/native.tsx`](../src/web/components/native.tsx)), and
every one gets its swipe from one hook, `useSheetDrag`
([`src/web/sheetDrag.ts`](../src/web/sheetDrag.ts)). The approach and the
numbers are ported from Hungry (`juncaj93/Hungry`, `src/ui/sheet.js` and
`assets/tokens.css`), whose sheet the owner rates as the one to match. The
math is unit-tested in `tests/sheetDrag.test.ts`; the gesture is covered under
touch in `e2e/sheet-swipe.spec.ts` at all four widths, with
`e2e/sheet-interaction.spec.ts`, `e2e/sheet-vs-pull.spec.ts` and
`e2e/player-card-scroll.spec.ts` around it.

| Rule | Value | From |
| --- | --- | --- |
| Movement before a touch is judged | 4px | Hungry |
| Card follows the finger | 1:1, measured from where the drag engaged | Hungry |
| Past 160px of finger | the card takes 0.35 of each further pixel | Hungry |
| Release closes it | past 28% of the card's height or 140px, whichever is less | Hungry |
| …or a flick | 0.5 px/ms downward over the last 120ms, once past 16px | added |
| An upward flick | keeps the card, even past the line | added |
| Upward drag | rubber-bands, never more than 6px | added |
| Dim layer | clears in step with the card, fully at 400px or the card's height | Hungry |
| Close | 240ms from where the card is, `cubic-bezier(0.22, 0.61, 0.36, 1)` | Hungry |
| Spring back | 240ms, `cubic-bezier(0.34, 1.12, 0.64, 1)` (a couple of px of overshoot) | milder Hungry spring |

**Where a drag may start.** The grip and the header always (`touch-action:
none` on both). The body only when it, and everything between the finger and
the card, is scrolled to the top and the first clear movement is downward. A
sideways first movement, an upward one, a scrolled body or a text field all
leave the gesture to the browser for the rest of the touch, so reading a card
never closes it.

**Why touch events.** iOS Safari lets a page claim a drag only by calling
`preventDefault` on a non-passive `touchmove`. Pointer events are cancelled the
moment Safari decides the movement is a scroll. The sheet listens to touches
and calls `preventDefault` only once a drag is its own; the movements under
4px are never cancelled, so a pixel of drift before a flick up still scrolls.

**The page behind.** `useOverlay` pins it. The backdrop declares `touch-action:
none`, and the body `overscroll-behavior: contain`, so nothing rubber-bands
the page or starts a pull-to-refresh under a sheet. The app's own
pull-to-refresh and back swipe stand down while any layer is open.

**Other ways out.** Done, a tap on the backdrop and Escape all close the card
with the same 240ms exit. Reduced motion closes and springs back without
animating.

## 7. What is deliberately absent

- **No service worker.** Standalone display does not need one, and an offline
  cache for an app whose whole value is live draft state would be a liability,
  not a feature.
- **No native wrapper.** No Capacitor, no WKWebView shell, no App Store.
- **No `orientation` lock** in the manifest.

## 8. Troubleshooting

| Symptom | Cause |
| --- | --- |
| The Home Screen icon opens a Safari tab with a URL field | The manifest was not read at install time. Re-add from Safari; check `node scripts/probe-pwa.mjs <url>` passes. |
| Generic or blank Home Screen icon | `apple-touch-icon.png` did not resolve. Safari caches the failure; delete the icon and re-add. |
| A grey bar under the nav **in a Safari tab** | Expected. It is Safari's. See §1. |
| A grey bar under the nav **in standalone mode** | A real bug if it is taller than the gap the toolbar floats by. Open Setup → Install on iPhone → Layout diagnostics and read "Below the toolbar" — it says which it is. |
| Light-mode flash when launching | The manifest's `background_color` is the dark page colour; a light-theme user sees one dark frame. The alternative is a white flash into a dark app, which is worse. |
| A sheet will not swipe away, and the page behind it moves instead | Pull-to-refresh is taking the gesture. The overlay's covered signal is not reaching `usePullToRefresh` — see rule 6 on that hook in `src/web/gestures.ts`. |

`node scripts/probe-pwa.mjs <url>` checks every install prerequisite against a
running deployment — page metadata, manifest, content types, icon sizes,
`start_url`, HTTPS. The deploy workflow runs it after every release.
